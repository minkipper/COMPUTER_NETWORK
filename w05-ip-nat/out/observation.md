# 5주차 실습 관찰 보고서 (Week 5 Lab Observations)

## Task 1 · 서브넷과 최장 프리픽스 매칭 (Subnets and Longest-Prefix Match)
1. **`/31` 및 `/32` 대역의 반환값 설계와 이유**:
   - 일반 서브넷(`/0` ~ `/30`)은 네트워크 주소와 브로드캐스트 주소를 제외한 `(network + 1, broadcast - 1, broadcast)`를 반환하지만, `/31`은 호스트 비트가 1비트뿐이어서 이 공식을 그대로 적용하면 사용 가능한 주소가 0개가 됩니다. 따라서 **RFC 3021**(점대점 링크에서의 31비트 프리픽스 사용 표준)에 따라 두 주소 모두를 사용 가능한 호스트로 인정하여 `(network, broadcast, None)`을 반환하도록 구현했습니다.
   - `/32`는 단일 호스트 자체를 가리키는 경로(Host Route)이므로 첫 주소와 마지막 주소를 모두 자기 자신(`network`)으로 두고 브로드캐스트 주소는 `None`으로 반환했습니다.
2. **`10.20.30.70`이 매칭된 4개의 엔트리와 승자 결정 규칙**:
   - 목적지 `10.20.30.70`은 테이블 내의 `0.0.0.0/0` (`default-gw`), `10.0.0.0/8` (`campus`), `10.20.0.0/16` (`eng-building`), `10.20.30.0/24` (`lab-floor`), `10.20.30.64/26` (`lab-rack-2`) 중 `10.x` 대역 4개(기본 경로 포함 시 총 5개)의 서브넷 마스크 조건을 동시에 만족합니다.
   - 라우터는 매칭된 후보들 중 **가장 구체적인(프리픽스 길이가 가장 긴) 경로를 선택하는 최장 프리픽스 매칭(Longest-Prefix Match, LPM)** 규칙에 따라 `/26` 프리픽스를 가진 `10.20.30.64/26` (`lab-rack-2`)을 최종 다음 홉(Next Hop)으로 결정합니다.
3. **동일한 프리픽스 길이와 네트워크를 가진 중복 경로 처리**:
   - 동일한 `(network, prefix)`에 대해 서로 다른 Next Hop이 들어오는 것은 잘못 구성된(malformed) 라우팅 테이블이므로, `ForwardingTable.add()` 단계에서 중복 여부를 검사하여 즉시 `ValueError("duplicate route")` 예외를 발생시켜 모호성을 원천 차단했습니다.

## Task 2 · 내 네트워크 주소 분석 및 DHCP 캡처 (Where Exactly Are You?)
1. **거치고 있는 NAT의 계층 수와 그 근거**:
   - WSL2 컨테이너(`172.18.53.0/20`)와 Windows 물리 테더링 인터페이스(`10.103.141.198/24`) 및 유선 랜(`192.168.0.12/24`)은 모두 RFC 1918 사설 IP 대역인 반면, 외부 서버(`api.ipify.org`)가 관측한 공인 IP는 `39.127.58.218`(`campus wifi`) 및 `211.235.80.224`(`tethering`)입니다.
   - WSL2 내부 기준으로는 ① Hyper-V 가상 스위치 NAT(`172.18.53.0/20` $\rightarrow$ Windows 호스트 `10.103.141.198/24`)와 ② 스마트폰 핫스팟/공유기 및 통신사 CGNAT(`10.103.141.198` $\rightarrow$ `211.235.80.224`)를 거치므로 **최소 2겹 이상의 다중 NAT(Multi-layer NAT)** 뒤에 있으며, 첫 번째 게이트웨이(`172.18.48.1`)를 지난 다음 홉(`10.103.141.108` / `192.168.0.1`) 역시 RFC 1918 사설 IP라는 점이 다중 NAT의 명확한 증거입니다.
2. **두 네트워크(`campus wifi` vs `tethering`) 사이에서 변한 것과 변하지 않은 것, 그리고 이유**:
   - 네트워크를 `campus wifi`에서 모바일 `tethering`으로 전환하자, 최상위 ISP 출구 NAT 라우터가 바뀌어 **외부 공인 IP가 `39.127.58.218`에서 `211.235.80.224`로 완전히 변경**되었고, Windows 물리 어댑터의 사설 IP와 게이트웨이도 각 로컬 DHCP 서버의 주소 풀에 따라 `192.168.0.12/24`(GW `192.168.0.1`)에서 `10.103.141.198/24`(GW `10.103.141.108`)로 변경되었습니다.
   - 반면 WSL2 내부에서 수집한 로컬 IP(`172.18.53.0/20`)와 게이트웨이(`172.18.48.1`)는 변하지 않았는데, 이는 호스트의 물리 인터페이스가 바뀌어도 WSL2 가상 머신은 호스트 내부의 고정된 Hyper-V 가상 스위치 서브넷(`172.18.48.0/20`)에 연결된 상태를 그대로 유지하기 때문입니다.
3. **DHCP Discover의 출발지 주소와 다른 값일 수 없는 이유**:
   - 실제 캡처한 `out/dhcp.pcapng`의 Discover 패킷(Frame #2)은 출발지 IP가 `0.0.0.0`, 목적지 IP가 `255.255.255.255`(Lease Time은 Offer 기준 `3600`초)입니다.
   - 클라이언트가 네트워크에 처음 진입하여 IP를 요청하는 시점에는 **아직 할당받은 자신의 IP 주소가 전혀 없고 DHCP 서버의 주소도 모르기 때문에**, RFC 2131 규격에 따라 출발지는 미지정 주소인 `0.0.0.0`일 수밖에 없으며, 목적지 또한 서브넷 전체에 도달하는 제한된 브로드캐스트(`255.255.255.255`)를 사용할 수밖에 없습니다.

## Task 3 · 고속 최장 프리픽스 매칭 구현 (Make Longest-Prefix Match Fast)
1. **선택한 자료구조와 메모리 비용**:
   - 프리픽스 길이별로 해시 테이블(`dict`)을 분리하고, 실제 테이블에 존재하는 프리픽스 길이(`plen`)들만 내림차순(가장 긴 프리픽스부터 짧은 순서)으로 정렬해 탐색하는 **Prefix-Length Grouped Hash Table** 구조를 선택했습니다.
   - 각 경로는 `network >> (32 - plen)` 형태의 정수 키와 `next_hop` 값의 쌍으로 딕셔너리에 정확히 한 번씩만 저장되므로, 메모리 복잡도는 엔트리 수 $N$에 비례하는 $\mathcal{O}(N)$입니다(5,000개 경로 기준 수백 KB 이내의 매우 작은 오버헤드).
2. **탐색 시간 복잡도의 상한 (R5: What bounds your lookup now?)**:
   - 기존 `LinearTable`의 탐색 시간은 전체 경로의 개수 $N$(5,000개)에 비례하는 $\mathcal{O}(N)$이었으나, 구현한 [`YourTable`](file:///C:/Users/minki/OneDrive/Desktop/%EC%BB%B4%ED%93%A8%ED%84%B0%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%81%AC_%EA%B3%BC%EC%A0%9C/2026-lecture-network-practice-main/w05-ip-nat/task3_lpm.py#L40-L77)의 탐색 시간은 라우팅 테이블 크기 $N$과 무관하며 **활성화된 서로 다른 프리픽스 길이의 개수 $L$ ($L \le 33$)**에 비례하는 $\mathcal{O}(L)$로 제한됩니다.
   - 긴 프리픽스부터 해시 조회($\mathcal{O}(1)$)를 수행하다가 첫 번째 매칭이 발생하는 즉시 탐색을 종료(Early Exit)하므로, 트래픽의 대부분을 차지하는 `/24` 매칭은 단 첫 번째 확인에서 바로 반환되어 기존 대비 **약 1,815배** 빠른 초당 673만 건(`6,732,148 lookups/s`)의 성능을 달성했습니다.
3. **Python에서는 해시 테이블이 더 빠름에도 실제 라우터 하드웨어가 Bit-Walk(Trie) 방식을 사용하는 이유**:
   - Python은 인터프리터 언어 특성상 비트 단위로 포인터를 따라가는 트라이(Trie)를 순회하면 매 비트마다 Python 객체 참조와 루프 오버헤드가 발생하는 반면, `dict` 해시 조회는 C로 최적화된 내부 루틴을 한 번만 호출하므로 해시 테이블이 훨씬 빠릅니다.
   - 반면 실제 하드웨어 라우터(ASIC/FPGA)에서 해시 테이블을 쓰면 해시 함수 연산 지연과 **해시 충돌(Collision)로 인해 최악의 경우(Worst-case) 탐색 시간을 일정하게 보장할 수 없어** 회선 속도(Line-rate) 패킷 처리가 깨질 수 있습니다. 반면 멀티비트 트라이(Multi-bit Trie)나 TCAM 기반의 비트 탐색은 SRAM 메모리뱅크 파이프라이닝을 통해 매 클럭 사이클마다 결정론적인(Deterministic) 시간 안에 100% 예측 가능한 지연을 보장하기 때문에 하드웨어에서는 트라이/TCAM 구조를 사용합니다.
