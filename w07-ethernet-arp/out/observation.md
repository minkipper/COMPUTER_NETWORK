# 7주차 실습 관찰 보고서 (Week 7 Lab Observations · Ethernet, ARP and Switching)

## Task 1 · 자가 학습 스위치 구현 (A Learning Switch)

1. **프레임이 들어온 입력 포트(`in_port`)로 절대 다시 내보내지 말아야 하는 이유와 위반 시 발생하는 현상**:
   - 이더넷(Ethernet) 프레임 헤더에는 IP 헤더의 **TTL(Time-To-Live)이나 홉 카운트 필드가 존재하지 않습니다**. 또한 동일한 포트(동일 세그먼트)에 연결된 목적지 호스트는 스위치의 중계 없이도 이미 물리 매체/하위 세그먼트 상에서 해당 프레임을 직접 수신한 상태입니다.
   - 만약 스위치가 들어온 포트로 프레임을 다시 내보내면(Hairpinning/Echo), ① 목적지 호스트가 **동일한 프레임의 중복 복사본(Duplicate Frame)**을 수신하게 되고, ② 두 대 이상의 스위치가 연결된 토폴로지에서는 두 스위치가 미학습 프레임이나 브로드캐스트 프레임을 서로에게 무한히 반사시키는 **2계층 브로드캐스트 스톰(Broadcast Storm / Switching Loop)**이 즉시 발생하여 링크 대역폭과 스위치 CPU를 수 밀리초 만에 100% 고갈시킵니다.
2. **목적지를 모를 때 스위치는 플러딩(Flooding)하고 라우터는 폐기(Drop)하는 이유**:
   - **스위치(2계층, Plug-and-Play 평면 주소)**: MAC 주소는 위치 정보가 없는 평면(Flat) 식별자이며, 스위치는 라우팅 프로토콜(OSPF/BGP 등) 없이 스스로 조용히 프레임을 관찰해 테이블을 채웁니다(Self-learning). 따라서 아직 한 번도 말하지 않은 호스트의 위치는 알 방법이 없으므로, 일단 모든 포트로 **플러딩(Flooding)**해 목적지가 응답하게 만들어야만 비로소 그 호스트의 위치를 학습할 수 있습니다(한 로컬 브로드캐스트 도메인 내부로 범위가 제한되므로 플러딩이 가능함).
   - **라우터(3계층, 계층적 프리픽스 주소 및 전역 인터넷)**: 반면 라우터는 사전 교환된 라우팅 프로토콜(제어 평면)을 통해 모든 도달 가능한 네트워크 프리픽스를 미리 알고 있어야 하며, 전 세계 수십억 대의 호스트가 연결된 인터넷에서 알 수 없는 IP 패킷을 모든 인터페이스로 플러딩하면 인터넷 전체가 마비됩니다. 또한 IP 헤더에는 TTL이 있어 잘못된 경로를 떠도는 패킷을 조기에 제거해야 하므로, 라우팅 테이블에 매칭되지 않는 패킷은 즉시 **폐기(Drop)**하고 `ICMP Destination Unreachable`을 반환합니다.
3. **타임아웃 기반 에이징(Aging)의 한계와 "더 직접적인(More direct)" 방법**:
   - **타임아웃 에이징이 잃는 것**: 타임아웃(`AGE_SECONDS = 300`초)은 호스트가 실제로는 같은 포트에 그대로 연결되어 단지 **조용히 침묵(Idle)하고 있는 경우**와 **케이블을 뽑아 다른 포트로 이동하거나 전원을 끈 경우**를 구분하지 못합니다. 따라서 ① 300초 이상 수신 전용으로만 동작하거나 유휴 상태인 정상 서버로 가는 유니캐스트 트래픽이 만료 직후 불필요하게 모든 포트로 플러딩되며, ② 반대로 호스트가 이동한 뒤 새 포트에서 말하기 전까지의 최대 300초 동안은 옛날 포트로 프레임이 잘못 전달(Black-hole)됩니다.
   - **더 직접적인 방법**: 시간 추측 대신 **물리 계층(L1)의 링크 캐리어 상태 감지(Link-Down Interrupt)**를 사용하여 해당 포트의 케이블이 뽑히는 즉시 그 포트에 매핑된 MAC 엔트리를 삭제하거나, 관리형 네트워크에서는 **802.1X 포트 인증 해제 / LLDP 프레임 / 무선 AP 로밍 시의 Gratuitous ARP(GARP)** 통지를 받아 즉시 갱신하는 것이 더 직접적인 해법입니다.

## Task 2 · 실제 ARP 동작 관찰 및 캡처 (Watch ARP Happen)

### Part A · ARP 테이블 초기화 및 재충전 (`out/arp-before.txt`, `out/arp-after.txt`)
1. **A2 — 초기화 후 가장 먼저 다시 나타난 엔트리와 그 이유**:
   - ARP 캐시를 완전히 비운(`ip -s -s neigh flush all`) 직후 가장 먼저(그리고 유일하게) 다시 나타난 엔트리는 **기본 게이트웨이(Default Gateway)인 `172.18.48.1` (`00:15:5d:de:76:52`)**입니다.
   - 호스트가 서브넷 내부든 외부 인터넷이든 첫 번째 IP 패킷을 전송하려면 이더넷 프레임의 목적지 MAC 주소를 채워야 하는데, 모든 외부/게이트웨이 통신의 첫 홉(First Hop)이 기본 게이트웨이이므로 커널이 첫 패킷을 내보내기 직전 반드시 게이트웨이 IP(`172.18.48.1`)에 대한 ARP Request를 가장 먼저 브로드캐스트하기 때문입니다.
2. **A3 — 초기화 전(`before`)과 후(`after`)의 엔트리 수 비교 및 차이 원인**:
   - [`out/arp-before.txt`](file:///C:/Users/minki/OneDrive/Desktop/%EC%BB%B4%ED%93%A8%ED%84%B0%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%81%AC_%EA%B3%BC%EC%A0%9C/2026-lecture-network-practice-main/w07-ethernet-arp/out/arp-before.txt)에는 과거 로컬 서브넷 통신 흔적인 `172.18.48.254`와 `172.18.48.1` 총 **2개**의 엔트리가 있었으나, 캐시를 비운 뒤 게이트웨이 `ping`과 `https://www.korea.ac.kr` 접속을 마친 [`out/arp-after.txt`](file:///C:/Users/minki/OneDrive/Desktop/%EC%BB%B4%ED%93%A8%ED%84%B0%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%81%AC_%EA%B3%BC%EC%A0%9C/2026-lecture-network-practice-main/w07-ethernet-arp/out/arp-after.txt)에는 **`172.18.48.1` 단 1개**만 존재합니다.
   - 이는 ARP 테이블이 **요청 시점(On-demand)에만 채워지는 소프트 상태(Soft State) 캐시**이기 때문입니다. 초기화 이후 우리가 실제로 트래픽을 보낸 로컬 링크 상의 이웃은 기본 게이트웨이(`172.18.48.1`)뿐이므로, 다시 통신하지 않은 `172.18.48.254`는 테이블에 재등장하지 않습니다.
3. **A4 — 외부 웹 서버(`www.korea.ac.kr`)에 접속했음에도 ARP 테이블에 해당 서버가 없는 이유**:
   - **ARP는 오직 동일한 로컬 서브넷(동일 L2 브로드캐스트 도메인 / 링크) 내에 직접 연결된 이웃의 MAC 주소만 해석하는 프로토콜**이기 때문입니다.
   - 내 호스트(`172.18.53.0/20`)가 외부 인터넷에 있는 `www.korea.ac.kr`(`163.152.6.10`)로 IP 패킷을 보낼 때, 라우팅 테이블 조회 결과 목적지가 내 서브넷 밖이므로 **다음 홉(Next Hop) IP는 원격 서버가 아니라 내 기본 게이트웨이(`172.18.48.1`)**로 결정됩니다. 따라서 3계층 IP 헤더의 목적지 주소는 `163.152.6.10`이지만, 2계층 이더넷 프레임의 목적지 MAC 주소에는 **기본 게이트웨이(`172.18.48.1`)의 MAC 주소(`00:15:5d:de:76:52`)**를 넣어야 하며, 이 때문에 지구 반대편의 수천 개 웹 서버와 통신하더라도 내 ARP 테이블에는 오직 로컬 게이트웨이 엔트리 하나만 유지됩니다.

### Part B · 와이어 상의 ARP Request 및 Reply 분석 (`out/arp.pcapng`)
1. **B1 & B2 — 캡처된 ARP Request와 Reply의 목적지 MAC 주소 비교**:
   - [`out/arp.pcapng`](file:///C:/Users/minki/OneDrive/Desktop/%EC%BB%B4%ED%93%A8%ED%84%B0%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%81%AC_%EA%B3%BC%EC%A0%9C/2026-lecture-network-practice-main/w07-ethernet-arp/out/arp.pcapng)에서 캡처된 두 패킷의 이더넷 목적지 주소는 다음과 같이 주소의 종류 자체가 다릅니다:
     - **Frame #1 · ARP Request (`opcode = 1`, Who has `172.18.48.1`? Tell `172.18.53.0`)**:
       - 이더넷 목적지 MAC (`eth.dst`): **`ff:ff:ff:ff:ff:ff` (L2 브로드캐스트 주소)** (ARP 페이로드 내 Target MAC은 미지정 상태인 `00:00:00:00:00:00`)
     - **Frame #2 · ARP Reply (`opcode = 2`, `172.18.48.1` is at `00:15:5d:de:76:52`)**:
       - 이더넷 목적지 MAC (`eth.dst`): **`00:15:5d:f4:05:68` (요청 호스트의 L2 유니캐스트 주소)**
2. **B3 — 두 목적지 주소의 의미와 수신 대상의 비대칭성**:
   - **ARP Request (`ff:ff:ff:ff:ff:ff`)**: 요청 시점에는 누가 `172.18.48.1`을 가지고 있는지 전혀 모르기 때문에, 스위치가 이 프레임을 **같은 LAN 세그먼트에 연결된 모든 호스트에게 플러딩**하도록 브로드캐스트 주소를 사용합니다(세그먼트 내 모든 호스트가 수신).
   - **ARP Reply (`00:15:5d:f4:05:68`)**: 반면 `172.18.48.1`(게이트웨이)은 방금 받은 ARP Request 안에 적혀 있던 질문자의 출발지 IP/MAC(`172.18.53.0` / `00:15:5d:f4:05:68`)을 이미 알게 되었으므로, 불필요하게 다른 호스트들을 깨우지 않고 **오직 질문한 호스트 한 대에게만 유니캐스트로 응답**합니다.
3. **B4 — 1분간의 ARP 트래픽 양과 캠퍼스 규모 세그먼트로 확장 시의 한계**:
   - 단일 호스트 환경에서 캐시 초기화 후 1분간 발생한 ARP 패킷은 왕복 **2개**(Request 1개, Reply 1개)뿐이지만, 이 중 **ARP Request 1개는 브로드캐스트이므로 세그먼트 내의 모든 $N$개 포트와 호스트의 NIC/CPU에 전달**됩니다.
   - 만약 하나의 거대한 평면(Flat) L2 캠퍼스 네트워크에 $N = 5,000$대의 기기가 연결되어 있고 각 기기가 분당 평균 2회의 ARP Request만 발생시켜도, 모든 호스트는 분당 $10,000$개(초당 약 167개)의 브로드캐스트 인터럽트를 처리해야 하며, 스위치 전체 포트($5,000$개)에서 복사되어 나가는 프레임 수는 분당 $10,000 \times 5,000 = \mathbf{5,000\text{만 개}}$에 달합니다. 바로 이 $\mathcal{O}(N^2)$ 브로드캐스트 오버헤드 때문에 대규모 캠퍼스 망은 단일 L2로 묶지 않고 **VLAN과 3계층 서브넷(라우터)으로 브로드캐스트 도메인을 분할**합니다.

## Task 3 · 용량이 부족한 스위치의 교체 및 입장 정책 (A Switch That Runs Out of Room)

1. **설계한 교체(Eviction) 규칙과 이를 위해 유지하는 증거(Evidence)**:
   - [`YourSwitch`](file:///C:/Users/minki/OneDrive/Desktop/%EC%BB%B4%ED%93%A8%ED%84%B0%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%81%AC_%EA%B3%BC%EC%A0%9C/2026-lecture-network-practice-main/w07-ethernet-arp/task3_flooding.py#L46-L115)에서는 단순 도착 순서(FIFO) 대신 **누적 트래픽 관측 빈도(LFU: Least Frequently Used)와 최근 시각(LRU tie-breaker)을 결합한 교체 규칙**을 사용합니다.
   - 이를 위해 각 프레임이 지나갈 때마다 출발지(`src`)와 유니캐스트 목적지(`dst`) MAC이 등장한 횟수를 `self.freq[mac]`에 기록하고 마지막 관측 시각을 `self.last_seen[mac]`에 기록합니다. 테이블(`self.table`, 최대 64개)이 가득 찼을 때는 현재 테이블 거주자 중 **`(self.freq[m], self.last_seen[m])`이 가장 작은(가장 덜 활발하고 가장 오래된) 엔트리를 교체 후보(`victim`)로 선정**합니다.
2. **신규 출발지 학습 거절(Declining Admissions) 여부와 적용 전후 수치 비교**:
   - **예, 조건부 입장 통제(Frequency-Gated Admission Control)를 적용하여 자격 미달인 신규 출발지의 학습을 거절했습니다.**
   - 테이블이 이미 64개로 가득 찬 상태에서 새로운 `src`가 도착했을 때, 무조건 기존 거주자(`victim`)를 쫓아내고 `src`를 넣으면 단 한 번 말하고 사라질 롱테일(One-shot) 호스트가 상위 인기 호스트의 자리를 빼앗아 이후 인기 호스트로 향하는 수많은 프레임이 47개 포트로 플러딩됩니다. 따라서 **`self.freq[src] > self.freq[victim]`(신규 호스트의 누적 활동 빈도가 테이블 내 최하위 거주자보다 높음이 입증된 경우)에만 교체를 허용하고, 그렇지 않으면 학습을 거절(Decline)**했습니다.
   - **수치 변화 비교 (`out/bench.txt`)**:
     - Baseline (`NaiveSwitch`, 무조건 학습 + FIFO 교체): `wasted = 323,380`
     - 무조건 학습 + 빈도 감쇠 교체 (Admission 거절 없이 약한 엔트리 교체): `wasted = 187,864` (**41.9% 절감**, `good` 등급)
     - **빈도 기반 입장 거절 적용 (`YourSwitch`, LFU + Admission Control)**: `wasted = 156,814` (**51.5% 절감, 표기 `52%`, 최고 등급 `strong`** — 400개 호스트 중 상위 64개를 완벽히 미리 알고 고정했을 때의 이론적 한계치인 `152,490`[`52.8%` 절감]에 사실상 근접!).
3. **R6 — 이 테이블 구조를 악용한 공격 시나리오(MAC Flooding Attack)와 스위치의 방어책**:
   - **공격 방식과 스위치의 반응**: 스위치의 MAC 주소 테이블(CAM 테이블) 크기가 고정되어 있고 테이블에서 밀려난 목적지로 가는 프레임은 **모든 포트로 플러딩(Flooding)**된다는 점을 아는 공격자는, 자신의 포트에서 **매 프레임마다 무작위로 위조한(Spoofed) 수천~수만 개의 가짜 출발지 MAC 주소**로 프레임을 대량 전송합니다(**MAC Flooding / CAM Table Overflow 공격**).
   - 기본 스위치(`NaiveSwitch`)는 무조건 새로 들어온 출발지 MAC을 학습하므로, 순식간에 테이블의 64개 슬롯 전체가 공격자의 가짜 MAC 주소들로 가득 차고 **정상 호스트들의 실제 MAC 엔트리는 전부 테이블에서 쫓겨납니다(Evicted)**. 그 순간부터 정상 호스트들끼리 주고받는 모든 유니캐스트 프레임은 스위치에서 "미학습 목적지"로 분류되어 **공격자의 포트를 포함한 모든 포트로 플러딩**되며, 스위치는 사실상 보안 기능이 없는 1계층 허브(Hub)로 전락하여 공격자가 타인의 평문 트래픽을 모두 도청(Sniffing)할 수 있게 됩니다.
   - **스위치가 취할 수 있는 방어책 (Port Security / Per-Port MAC Limit)**: 스위치의 각 물리 포트별로 **학습을 허용할 최대 MAC 주소 개수(예: 포트당 1~3개)를 제한하는 포트 보안(Port Security)** 기능을 적용하거나, 본 과제에서 구현한 것처럼 단일 포트에서 한 번씩만 등장하는 일회성 MAC 주소가 기존에 검증된 다빈도 호스트 엔트리를 밀어내지 못하도록 **입장 통제(Admission Control) 및 포트별 학습 속도 제한(Rate-limiting)**을 걸어두면 공격자의 가짜 MAC들이 다른 포트의 정상 엔트리를 오염시키는 것을 원천 차단할 수 있습니다.
