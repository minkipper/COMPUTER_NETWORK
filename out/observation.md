# 3주차 실습 관찰 보고서 (Week 3 Lab Observations)

## Task 1 · 반복적 DNS 리졸버 (Iterative Resolver)
1. **루트 서버가 곧바로 최종 주소를 반환하지 않는 이유**: 전 세계 수십억 개에 달하는 모든 호스트의 매핑 정보를 단 13개(Anycast 인스턴스 포함) 루트 서버가 유지하는 것은 확장성(Scalability) 관점에서 불가능하며, 부하 집중 및 단일 장애점(SPOF) 문제를 방지하기 위해 계층적 분산 구조를 취하고 있습니다. 따라서 루트 서버는 최종 IP 대신 TLD(.kr, .com 등)를 관할하는 네임서버 목록으로 위임(Delegation)합니다.
2. **글루 레코드(Glue Record) 부재 시 처리 및 추가 비용**: 권한 위임 응답의 `ADDITIONAL` 섹션에 네임서버의 IP가 없는 경우(No glue), 해당 네임서버의 호스트명을 찾기 위해 루트부터 다시 반복 질의하는 재귀적 조회 과정이 발생합니다. 이로 인해 한 단계 위임 시마다 최소 2~4회의 추가 RTT 질의 비용이 소모됩니다.
3. **질의 서버 수와 일반 PC 환경의 비교**: `www.microsoft.com`과 같은 다단계 CNAME 및 CDN 기반 도메인을 조회할 때 루트→TLD→권한 서버→CNAME 대상 도메인 권한 서버까지 총 10개 이상의 네임서버를 직접 거쳐야 했습니다. 반면 일반 노트북 환경에서는 로컬 캐싱 재귀 리졸버(ISP 리졸버 등)에 단 1번만 재귀 질의(+recurse)를 전송하고 최종 응답을 수신하므로 클라이언트의 네트워크 비용이 대폭 절감됩니다.

## Task 2 · DNS Steering 및 CDN 계층 분석
1. **제3자(Third-party) CDN 분류 규칙**: CNAME 체인을 최종 대상까지 추적했을 때, 최종 도메인의 소유 영역(Domain Zone)이 질의한 원본 도메인의 소유 영역과 다르면 제3자 CDN 호스팅으로 판정하고, CNAME이 없거나 원본 도메인 내부에서 끝나면 자체(own) 또는 일반 호스팅으로 판정했습니다.
2. **규칙이 오판한 사이트와 원인**: `www.github.com`은 CNAME이 `github.com` 내부에서 종결되어 규칙상 자체 호스팅(`third_party: false`)으로 분류되었으나, 실제로는 Fastly Anycast CDN 인프라를 통해 서비스됩니다. 단순 CNAME 문자열 비교 규칙은 Anycast IP 라우팅 기반의 CDN을 식별하지 못하는 한계가 있습니다.
3. **스티어링 측정 결과 (Steering Number)**: 동일 네트워크 내 서로 다른 3개의 리졸버(System, Google 8.8.8.8, Quad9 9.9.9.9)에 질의했을 때, 제3자 CDN 호스팅 사이트 9개 중 7개 사이트가 서로 다른 IP 주소 집합을 반환하여(7 of 9 sites answered differently), DNS가 리졸버의 위치와 네트워크 경로에 맞춰 최적의 캐시 서버로 사용자를 유도(Steering)하고 있음을 확인했습니다.

## Task 3 · DNS 캐시 구현 및 성능 하한선 분석 (Cache Floor)
1. **기본 베이스라인 캐시(BaselineCache)의 두 가지 결함**:
   - **정확성 결함 (Correctness)**: 업스트림이 제공한 실제 레코드의 TTL을 무시하고 하드코딩된 고정 수명(60초)을 적용하여, TTL이 20~30초로 매우 짧은 CDN 레코드에 대해 이미 만료된 정보(Stale answers)를 266회나 반환하는 치명적인 결함이 있습니다.
   - **성능 결함 (Performance)**: 캐시 자료구조로 파이썬 리스트를 사용하여 매 조회마다 $O(N)$의 선형 탐색을 수행하고, TTL이 1시간~하루(3600s~86400s)에 달하는 장기 유효 레코드조차 60초 만에 캐시에서 삭제해 불필요한 업스트림 질의를 과도하게 유발합니다.
2. **최소 업스트림 질의 수 하한선(Floor)과 이론적 근거**:
   - 본 1,000개 쿼리(60분 워크로드)에서 어떠한 올바른 캐시도 도달할 수 있는 이론적 최소 업스트림 질의 횟수(Floor)는 정확히 **275회**입니다.
   - 특정 도메인의 캐시 만료 시각 $t_{expire} = t_{request} + TTL$ 이전에는 캐시된 데이터를 무조건 재사용할 수 있으나, 만료 시점 이후 처음 들어오는 질의는 만료된 데이터를 전달할 수 없으므로 반드시 업스트림에 다시 요청해야 합니다. 각 도메인별 질의 발생 시각 열에서 이전 수명 주기를 벗어난 횟수를 합산하면 $\sum \text{requests outside fresh window} = 275$회가 되며, 미래의 질의 시점을 미리 알지 못하는 이상(Causality) 이보다 적은 횟수로 stale=0을 달성하는 것은 불가능합니다. `YourCache`는 정확히 이 하한선(275회, 0 stale)을 달성했습니다.
3. **베이스라인이 가장 잘못 처리한 레코드**: `www.microsoft.com` (TTL: 20초)입니다. 실제 유효 기간이 20초에 불과하지만 60초 동안 캐시에 유지하여, 20초~60초 사이에 유입되는 수많은 요청들에 대해 가장 많은 양의 만료된 응답(Stale record)을 반환하게 되기 때문입니다.
